# 一次真实的线路排查记录：从「完全不通」到「稳定可用」

> 这份文档记录了一个真实项目从零部署到跑通的全过程，重点不是"成功经验"，
> 而是**踩过的 8 个坑**以及每个坑的**症状 → 诊断 → 根因 → 解法**。
>
> 如果你正在自建线路，这份记录可以帮你省下几个小时。
>
> **所有敏感信息（IP、UUID、密钥、密码、端口）均已用占位符替换。**

---

## 0. 先说结论：一张速查表

遇到问题先对表，能省掉大部分弯路：

| 症状 | 大概率原因 | 去做 |
| --- | --- | --- |
| ICMP 通、22 通、**其它端口全不通** | IP 被针对性封锁 | 换 IP 或换机房 |
| ICMP 通、22 通、443 不通，**服务端 `ss` 显示在监听** | 服务端 `ufw` 没放行 443 | `ufw allow 443/tcp` |
| 新开的机器 443 不通 | **正常现象** —— 还没装服务端，没人监听 | 装完服务端再测 |
| `REALITY: processed invalid connection`（几毫秒内失败） | 客户端与服务端参数不匹配（UUID / 公钥 / ShortId / flow） | 逐项比对 |
| 握手成功但 `connection reset by peer` | 伪装目标不可达，或线路对 TLS 有干扰 | 换伪装目标（如 `www.apple.com`） |
| 手机连不上电脑的代理 | 路由器/中继器做了设备隔离 | 两台设备都连主路由器 |
| `sing-box check` 通过但启动就 FATAL | 弃用字段需要环境变量放行，或运行期才校验 | 看 `journalctl` |
| 配置报 `legacy ... deprecated` | 客户端内核比服务端新，字段被移除 | 按迁移表逐个清理 |

## 1. 起点：服务端部署

### 1.1 环境

| 项目 | 选择 |
| --- | --- |
| 服务商 | Vultr |
| 机房 | 首尔（Seoul） |
| 配置 | 1 vCPU / 1 GB / 25 GB SSD / 1 TB 流量 |
| 系统 | Debian 12 x64 |
| 内核 | sing-box 1.11.15（服务端与客户端同版本最省事） |

### 1.2 部署方式：脚本写成文件再执行

**教训**：长脚本直接粘贴到 SSH 终端，很容易出现**串行、截断、重复执行**。

我们遇到过这些实际事故：

- 一段脚本粘贴后尾部混入了另一段脚本的字符
- 密钥生成被执行了两遍，导致「服务端私钥」和「打印出来的公钥」不是一对
- 最终表现为 `REALITY: processed invalid connection`，排查了很久才发现是密钥不配对

**正确做法**：

```bash
# 先写入文件（heredoc 内容不参与外层 shell 解析，更安全）
cat > /root/install.sh <<'SCRIPT'
#!/bin/bash
set -e
# ... 脚本内容 ...
SCRIPT

# 再执行
bash /root/install.sh
```

注意 `<<'SCRIPT'` 的引号：**加了引号**，heredoc 内部不做变量展开和命令替换，能避免绝大多数粘贴事故。

### 1.3 服务端配置要点

```json
{
  "inbounds": [
    {
      "type": "vless",
      "tag": "vless-in",
      "listen": "::",
      "listen_port": 443,
      "users": [{ "uuid": "<UUID>", "flow": "xtls-rprx-vision" }],
      "tls": {
        "enabled": true,
        "server_name": "www.apple.com",
        "reality": {
          "enabled": true,
          "handshake": { "server": "www.apple.com", "server_port": 443 },
          "private_key": "<服务端私钥>",
          "short_id": ["<ShortId>"]
        }
      }
    }
  ],
  "outbounds": [{ "type": "direct", "tag": "direct" }]
}
```

**两个细节**：

1. `listen: "::"` 让它同时监听 IPv4/IPv6，换 IP 后不用改配置
2. `flow` 字段**两边必须一致** —— 要么都写，要么都不写

## 2. 坑一：新机器 443 测不通就删机器

### 症状

新开的 Vultr 机器，`Test-NetConnection <IP> -Port 22` 通，`-Port 443` 不通。
连续删了三台机器，换了三个机房，全部如此。

### 根因

**一台刚装好系统的机器，443 端口本来就不通** —— 因为**没有任何程序在监听它**。

Debian 装好后默认只跑 `sshd`（监听 22）。443 要等 sing-box 装好并启动后才会有程序监听。

**测 443 得到的"不通"，和 IP 是否被封毫无关系。**

### 正确流程

```
① 开机器 → 测 22（通了说明机器活着、IP 可达）
② SSH 进去 → 装服务端
③ 装完 → 再测 443（这时候的结果才有意义）
```

**只有第 ③ 步不通，才需要换机器。**

> 这条如果早点知道，能省下三台机器的创建和销毁时间。

## 3. 坑二：Vultr 的 Debian 镜像默认开着 ufw

### 症状

```
客户端日志：dial tcp <IP>:443: i/o timeout
服务端：    systemctl is-active sing-box  →  active
           ss -lntp | grep 443            →  LISTEN *:443  sing-box
           Vultr 控制台 Firewall          →  No Firewall
```

服务端一切正常，但客户端连不上。**最诡异的是**：在服务器上抓包，能看到客户端发来的 SYN 包，**但服务器不回 SYN-ACK**：

```
tcpdump: 06:05:29 In  IP <客户端IP>.2952 > <服务器IP>.443: Flags [S]   ← SYN 到了
         06:05:30 In  IP <客户端IP>.2952 > <服务器IP>.443: Flags [S]   ← 重传，仍无响应
```

### 根因

```
iptables -L -n -v
Chain INPUT (policy DROP 462 packets, 33316 bytes)
  462 33316 ufw-reject-input        ← ufw 把包全拒了
```

**Vultr 的 Debian 镜像预装了 `ufw` 且已启用，默认只放行 22（SSH）。**
443 的 SYN 包到达后直接被 `ufw` 丢弃，所以内核不回 SYN-ACK —— 表现就是"连不上"。

### 解法

```bash
ufw allow 443/tcp        # VLESS / REALITY
ufw allow 8443/udp       # Hysteria2（如果用）
ufw reload
ufw status verbose
```

### 为什么这个坑特别坑

- **Vultr 控制台的 Firewall 显示 `No Firewall`** —— 那是**云端防火墙**，和系统里的 `ufw` 是两回事
- 服务端一切自检都正常（服务 active、端口在监听、日志无错）
- 症状和"IP 被墙"几乎一样，极易误判

**判断技巧**：`tcpdump` 能收到 SYN 但服务器不回 SYN-ACK → **优先怀疑本机防火墙**，而不是外部封锁。

## 4. 坑三：REALITY 参数不匹配

### 症状

```
服务端日志：inbound/vless[vless-in]: TLS handshake: REALITY: processed invalid connection
```

注意**耗时**，它是判断依据：

| 耗时 | 含义 |
| --- | --- |
| **几毫秒**（2～10ms） | 参数明显不对，REALITY 立刻判定非法 |
| 几秒（3～5s） | 尝试连接伪装目标后超时 |
| 几十秒 | 客户端等待超时（就是你感觉的"转了很久"） |

### 参数清单（必须两边一致）

| 参数 | 客户端 | 服务端 |
| --- | --- | --- |
| UUID | 链接里的 user 部分 | `users[0].uuid` |
| 公钥 / 私钥 | `pbk=` | `reality.private_key` 对应的公钥 |
| ShortId | `sid=` | `reality.short_id[0]` |
| SNI | `sni=` | `tls.server_name` 与 `reality.handshake.server`（**两处都要改**） |
| flow | `flow=` | `users[0].flow`（**要么都有，要么都没有**） |

### 教训：公钥必须从私钥推导，不能靠"记"

我们因为脚本重复执行，出现了「服务端私钥」和「对外公布的公钥」不配对的情况。
**唯一可靠的验证方式是从服务端私钥推导出公钥，再和客户端比对。**

推导方法（纯 Python，不依赖额外工具）：

```python
import base64
p = 2**255 - 19; A24 = 121665

def x25519(k_bytes, u_bytes):
    k = int.from_bytes(k_bytes,'little') & ((1<<255)-8)
    u = int.from_bytes(u_bytes,'little') & ((1<<255)-1)
    x1,x2,z2,x3,z3 = u,1,0,u,1; swap = 0
    for t in range(254,-1,-1):
        kt = (k>>t)&1; swap ^= kt
        if swap: x2,x3 = x3,x2; z2,z3 = z3,z2
        swap = kt
        a=(x2+z2)%p; aa=a*a%p
        b=(x2-z2)%p; bb=b*b%p
        e=(aa-bb)%p
        c=(x3+z3)%p; d=(x3-z3)%p
        da=d*a%p; cb=c*b%p
        x3 = pow((da+cb)%p,2,p)
        z3 = x1*pow((da-cb)%p,2,p)%p
        x2 = aa*bb%p
        z2 = e*((aa+A24*e)%p)%p
    if swap: x2,x3 = x3,x2; z2,z3 = z3,z2
    return (x2*pow(z2,p-2,p)%p).to_bytes(32,'little')

priv = '<服务端私钥>'
raw  = base64.urlsafe_b64decode(priv + '='*(-len(priv)%4))
pub  = base64.urlsafe_b64encode(x25519(raw, (9).to_bytes(32,'little'))).decode().rstrip('=')
print('PublicKey =', pub)
```

## 5. 坑四：伪装目标选得不好

### 症状

握手成功，但紧接着：

```
connection: report handshake success: go: connection reset by peer
```

或者服务端日志：

```
REALITY: failed to dial dest: dial tcp <某IP>:443: i/o timeout
```

### 根因

REALITY 需要**把它自己伪装成一个真实存在的 HTTPS 站点**。当认证失败时，它会把流量转发给那个"伪装目标"。

我们最初用 `www.microsoft.com`，它解析到 **Akamai 的 IP**，从服务器访问不稳定（时通时不通）。伪装目标的连接质量**直接影响握手成功率**。

### 解法

换成**从服务器所在地区访问稳定**的大站：

| 伪装目标 | 表现 |
| --- | --- |
| `www.microsoft.com`（Akamai） | ❌ 不稳定 |
| **`www.apple.com`** | ✅ **换上去就连通了** |
| `www.bing.com` | 备选 |
| `www.amazon.com` | 备选 |

**换 SNI 时记得两处都要改**：

```json
"tls": {
  "server_name": "www.apple.com",                              ← 这里
  "reality": { "handshake": { "server": "www.apple.com" } }     ← 还有这里
}
```

同时**客户端链接的 `sni=` 也要改**。

## 6. 坑五：改 SSH 端口差点把自己锁在门外

### 背景

因为 443 反复被干扰，决定把代理搬到 **22 端口**（22 从来没出过问题），SSH 挪到 22022。

### 事故发生

```bash
# 改了 SSH 端口
sed -i 's/^#*Port .*/Port 22022/' /etc/ssh/sshd_config
systemctl restart ssh
# 然后从电脑上连：
ssh -p 22022 root@<IP>
# → Connection timed out
```

**原因**：`ufw` 只放行了 22，**新端口 22022 没有放行**。

### 正确顺序（关键！）

```bash
# ① 先改 SSH 端口
sed -i 's/^#*Port .*/Port 22022/' /etc/ssh/sshd_config
systemctl restart ssh

# ② 立刻放行新端口（这一步千万别忘）
ufw allow 22022/tcp

# ③ 另开一个窗口验证新端口能登录（原窗口别关！）
#    ssh -p 22022 root@<IP>

# ④ 确认能登录后，再放行 22 给代理用
ufw allow 22/tcp

# ⑤ 最后才把代理改到 22 端口
```

**原则：改任何监听端口前，先确保自己有别的入口，并且防火墙同步放行。**

## 7. 坑六：sing-box 版本间的字段迁移

### 症状

同一份配置，在 1.11 上能用，在新版客户端上报各种错：

```
legacy DNS server formats are deprecated in sing-box 1.12.0 and removed in 1.14.0
legacy inbound fields are deprecated in sing-box 1.11.0 and removed in 1.13.0
gVisor is not included in this build, rebuild with -tags with_gvisor
outbound detour not found: direct
option "independent_cache" is deprecated in sing-box 1.14.0
option "stack" in TUN is deprecated in sing-box 1.15.0
```

### 根因

**服务端跑 1.11，手机客户端跑 1.15（开发版）**，中间跨越了 4 个大版本，字段被逐个移除。

**更麻烦的是**：`sing-box check` **不会报这些运行期问题**，只有真正启动服务时才暴露。

### 迁移对照表（我们实际改过的）

| 旧写法 | 新写法 | 弃用版本 |
| --- | --- | --- |
| DNS: `{"tag":"dns-local","address":"223.5.5.5"}` | `{"type":"udp","tag":"dns-local","server":"223.5.5.5"}` | 1.12 |
| DNS: `{"address":"https://1.1.1.1/dns-query"}` | `{"type":"https","server":"1.1.1.1"}` | 1.12 |
| DNS 规则: `{"server":"xxx"}` | 加 `"action":"route"` | 1.10 |
| 路由规则: `{"outbound":"xxx"}` | 加 `"action":"route"` | 1.10 |
| 入站: `"sniff": true` | 删除，改用路由 `{"action":"sniff"}` | 1.11 |
| DNS 服务器: `"detour": "direct"` | **删除**（新版内置 `direct` 标签不可引用） | — |
| 自己定义 `{"type":"direct","tag":"direct"}` | 删除（与内置标签冲突） | — |
| DNS: `"independent_cache": true` | 删除 | 1.14 |
| TUN: `"stack": "mixed"` | 删除（或改 `system`，且 1.15 起该字段整体弃用） | 1.15 |

### 关键教训

**① 客户端和服务端尽量用同一个大版本。** 跨版本调试会引入大量与网络无关的干扰项。

**② 装 `sing-box` 时优先选稳定版，别用 `dev` / rc 版本。** 开发版字段变动频繁。

**③ `check` 通过 ≠ 能启动。** 判断配置是否真的可用，必须**实际启动一次**并看日志。

**④ 错误信息越来越具体就是好消息。** 从"语法错误"到"字段 X 找不到"，说明方向是对的、在收敛。

## 8. 坑七：手机连不上电脑的代理

### 症状

手机设置好代理（`<电脑IP>:2080`），但：
- `http://<电脑IP>:2080` 打不开
- `http://ip-api.com/json` 显示的还是中国

### 排查过程（逐个排除）

| 检查 | 结果 | 排除 |
| --- | --- | --- |
| 电脑本机连自己 | `TcpTestSucceeded: True` | 代理本身没问题 |
| 防火墙配置文件 | 全部 `Enabled: False` | 不是防火墙 |
| 代理监听地址 | `0.0.0.0:2080`（开了局域网共享） | 监听正确 |
| 手机与电脑的网段 | 电脑 `192.168.1.8`，手机在 `192.168.11.x` | **← 找到了** |

### 根因：WiFi 中继器（信号放大器）

用户家里用了**WiFi 信号放大器**（几十块钱那种），它工作在 **WISP / 路由模式**：
- 自己又开了一层 NAT
- 手机连放大器的 SSID（`XXX-ext`），电脑连主路由器（`XXX`）
- **两个设备在不同网段，互相看不见**

**廉价中继器的通病**：设备隔离 + 带宽减半。

### 解法

**两台设备都连主路由器的 SSID**（不带 `-ext` 后缀的那个）。

在电脑上可以直接看到连接过的主网络名：

```powershell
netsh wlan show profiles
# 输出里能同时看到 xxx 和 xxx-ext，前者是主路由器
```

**另外注意**：换网络后电脑 IP 会变，手机代理要跟着改：

```powershell
(Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -like '*WLAN*' }).IPAddress
```

### 附：局域网共享的实现

要让手机连电脑代理，代理必须监听所有网卡（而不是只监听 `127.0.0.1`）：

```json
{
  "type": "mixed",
  "tag": "mixed-in",
  "listen": "0.0.0.0",        // 而不是 127.0.0.1
  "listen_port": 2080
}
```

并放行防火墙：

```powershell
New-NetFirewallRule -DisplayName '局域网共享' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 2080
```

## 9. 坑八：数据中心 IP 被目标站点风控

### 症状

- 电脑上 `curl` 访问目标站 → `HTTP 200` ✅
- 手机上通过同一线路 → 连接被重置 ❌

### 根因

**目标站点对数据中心 IP 段（VPS 服务商）有风控**。短时间密集请求后，连接会被立即 RST。

我们当时在反复尝试注册，几十次密集请求触发了这个限制。

### 表现特征

| 观察 | 说明 |
| --- | --- |
| 响应时间 ~330ms 后 `reset by peer` | TCP 和握手都成功了，是**应用层被重置** |
| 换目标站点（google 等）正常 | 说明隧道本身没问题 |
| 等几分钟后恢复 | 风控是**有状态**的，超时会自动解除 |

### 应对

| 方法 | 说明 |
| --- | --- |
| **降低请求频率** | 最有效 —— 别反复点"重试"、"重新发送验证码" |
| **失败后等 5～30 分钟** | 别硬刚，反复失败会加重风控 |
| **换节点/换机房** | 不同 IP 段的风控等级不同 |
| **换协议** | Hysteria2（UDP）与 TCP 的连接特征不同，有时能绕开 |

### 最重要的教训

> **遇到"突然全部不可达"，第一反应应该是"等几分钟"，而不是改配置。**

我们在这上面绕了很多弯路 —— 反复改配置、换端口、重启服务，其实只是需要等待。

**判断方法**：先测一个和目标站无关的境外站点（如 `google.com`）：
- 它通 → 隧道没问题，是目标站风控
- 它也不通 → 才是线路问题

## 10. 最终可用的架构

```
┌─────────────┐                    ┌──────────────┐                ┌─────────────┐
│  手机 App    │ ──┐                │              │                │             │
└─────────────┘   │   WiFi 局域网   │  Windows 客户端│   加密隧道     │  境外服务器  │──▶ 目标站点
                  ├───────────────▶│ (sing-box)   │ ─────────────▶ │ (sing-box)  │
┌─────────────┐   │   HTTP 代理     │              │                │             │
│  电脑浏览器   │ ──┘                └──────────────┘                └─────────────┘
└─────────────┘
```

| 组件 | 作用 |
| --- | --- |
| 境外服务器 | VLESS + REALITY（TCP）+ Hysteria2（UDP）双协议 |
| Windows 客户端 | Electron GUI + sing-box 内核，提供系统代理 / TUN / 局域网共享 |
| 手机 | 通过电脑的局域网代理上网（也可装客户端直连） |

**分流策略**：目标站点强制走代理（DNS 用加密 DoH 防污染），国内站点直连。

## 11. 排查方法论小结

这一路最有价值的可能是**排查思路**本身：

### ① 分层定位，别跳步

```
能 ping 通吗？        → 网络可达性
TCP 端口能连吗？      → 防火墙 / 封锁
TLS 握手成功吗？      → 协议参数
应用层能通吗？        → 目标站风控
```

每一层的现象和解法完全不同。**先确定卡在哪一层，再动手。**

### ② 抓包是终极手段

```bash
tcpdump -i any -nn 'tcp port 443' -c 30
```

看三个关键点：
- **SYN 到了吗？** → 没到 = 路上被挡；到了 = 本地问题
- **服务器回 SYN-ACK 了吗？** → 没回 = 本机防火墙丢弃
- **握手后数据正常往返吗？** → 断了 = 应用层/目标站问题

### ③ 保留对照实验

- 测国内站点（如 `baidu.com:443`）+ 测境外站点 → 区分"本地出网问题"和"目标不可达"
- 用另一个网络（手机热点）测同一目标 → 区分"你的网络问题"和"服务器问题"

### ④ 记录耗时

日志里的耗时数字是重要线索：

| 耗时 | 含义 |
| --- | --- |
| 几毫秒 | 本地立刻拒绝（参数错误/防火墙） |
| 几百毫秒 | 到达了对端，被应用层重置（风控） |
| 3～5 秒 | 超时（网络不通/目标无响应） |
| 几十秒 | 客户端等待（重传耗尽） |

### ⑤ 一次只改一个变量

我们犯过的错：同时改端口、换机房、改协议，结果出了问题不知道是哪个引起的。
